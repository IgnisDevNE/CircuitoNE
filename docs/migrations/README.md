# Migrações

Ainda não há SQL de negócio aplicado. Este é o diretório canônico solicitado pelo AGENTS.md. A primeira migração, `20260923160806_restrict_public_defaults.sql`, remove concessões automáticas a novos objetos públicos criados por `postgres`; cada objeto de negócio deve trazer grants e RLS explícitos. Ela não altera privilégios de objetos já existentes nem foi aplicada aos projetos hospedados.

O Supabase CLI procura `supabase/migrations`. `pnpm db:prepare` gera uma árvore temporária `temp/supabase-run-*` contendo `supabase/config.toml` e cópia somente de execução dos SQL de `docs/migrations/`. Essa árvore não é versionada nem editada manualmente. O CLI recebe `--workdir` apontando para ela. O CLI não lê `docs/migrations/` diretamente.

O adaptador preserva bytes, ordena nomes, rejeita versões duplicadas/nomes inválidos/links e grava checksums SHA-256 do config e de cada SQL em `manifest.json`. Cada execução recebe uma pasta nova; nenhum destino remoto ou argumento adicional é aceito. Não lê credenciais, chama o CLI ou executa reset. Os testes estão em `tests/migration-workdir.test.mjs`. Isso evita erros de preparo, mas não constitui isolamento contra um implementador capaz de alterar o script.

`supabase/config.toml` é apenas configuração de banco descartável (Postgres 17, porta 55432, API/Storage desligados). Auth está habilitado para que `db start/reset` execute as migrações oficiais do serviço antes das migrações da aplicação; o harness não inicia o servidor Auth nem envia mensagens. Não representa os projetos hospedados. Não copiar sua configuração para homologação/produção.

## Primeira fatia do schema — #116

`20260926213828_identity_profiles.sql` prepara identidade privada, quatro atuações, classificação musical, metadados de imagens e materiais. As RPCs `complete_registration`, `create_profile` e `set_default_artist` validam a identidade atual no banco; cliente não escreve diretamente nas tabelas. Cadastro exige Auth com e-mail/celular confirmado, idade mínima, CPF único válido e primeira atuação completa, na mesma transação. Reenvio idêntico com a mesma chave retorna o perfil inicial; chave ou payload divergente não cria nova primeira atuação. CPF só poderá mudar pelo procedimento de suporte da #23. Não há expiração arbitrária de cadastro Auth abandonado; definição/execução pertence à mesma issue.

`profiles` concede leitura somente das colunas do catálogo interno (`id`, `kind`, `name`, `description`, `city`, `state_code`). `get_profile` fornece os demais campos não profissionais apenas ao titular ou quando for artista publicado; nunca retorna `owner_id`. Não usar `select *` no catálogo. Contatos/materiais ficam em tabela separada, com RLS. A leitura profissional de terceiros permanece negada até a elegibilidade de proprietário da #117. As tabelas de arquivos impõem cotas, tipos e escopo do caminho; upload, validação dos bytes reais e URLs assinadas continuam em #21, sem escrita direta de metadados pelo cliente.

O snapshot SQL da taxonomia é comparado pelo teste à referência normativa JSON, sem uma segunda lista editável. `src/types/database.generated.ts` vem do `postgres-meta` fixado pela CLI, somente schema público; o CI compara o resultado com a reconstrução. `supabase/seeds/identity.sql` cobre estados ativo/suspenso/exclusão pendente, contatos não confirmados, quatro atuações e vários projetos artísticos, com IDs fixos e sem senhas utilizáveis. Exige destino sintético declarado pelo executor; isso não substitui a verificação do projeto e aprovação no workflow de homologação. Sua reaplicação não duplica nem sobrescreve registros existentes.

Validação inicial: PostgreSQL 17.6.1.167 e Auth v2.196.0 em container descartável sem rede externa; testes SQL positivos/negativos e seeds aplicados duas vezes. O harness Linux também reconstrói duas vezes e disputa CPF/cadastro em conexões concorrentes. #31 bloqueia aplicação remota; #32 exige posteriormente REST, seeds e smoke no dev protegido. Nenhum projeto hospedado recebe esta migração durante a preparação.

Para cada nova migração: CLI fixado em 2.117.0; conferir `--help` e os comandos disponíveis; gerar o nome via `supabase migration new` na árvore temporária e mover o SQL final para este diretório; gerar novamente a cópia de execução; testar reconstrução em banco descartável e aplicar no `CircuitoNE-dev` pelo GitHub após liberar os gates. A validação de arquivos e um ensaio sintético de reconstrução em Linux estão concluídos; schema/tipos/seeds reais e pipeline compartilhado ainda dependem de [#32](https://github.com/IgnisDevNE/CircuitoNE/issues/32) e do isolamento [#31](https://github.com/IgnisDevNE/CircuitoNE/issues/31).

Em 22/09/2026, a tentativa de banco local no Podman/Windows esbarrou no wrapper `docker.cmd` e depois no encaminhamento de rede WSL. O ensaio alternativo em container Linux passou com `pnpm test:database`: usa `supabase db start` e `supabase db reset --local` em pasta recém-criada, sem projeto vinculado nem credenciais remotas. A migração sintética `pipeline_probe` e o ID único do projeto existem apenas nessa cópia; o manifesto original descreve as entradas canônicas, não essas alterações exclusivas do teste. Confirmar comandos com `--help` na versão fixada. Não usar `--linked`, `--db-url` ou `--project-ref` para reset de testes. O helper não impede executar o CLI diretamente: a separação de credenciais continua obrigatória.

Cada migração de objeto de negócio deve incluir constraints, índices, grants, RLS, políticas e revogações necessárias. Acrescentar testes positivos e negativos e atualizar os tipos gerados. A migração inicial de privilégios altera apenas objetos futuros; não remove grants de objetos existentes. Recuperação normal: conceder explicitamente o privilégio requerido na migração do objeto ou em uma migração corretiva, sem reabrir a concessão automática geral. Após aplicada em ambiente compartilhado, não editar migração antiga: criar outra.

Promoção usa exatamente os mesmos bytes/ordem validados, registrados por checksum e SHA. Nunca resetar homologação compartilhada ou produção em CI. Mudanças destrutivas exigem plano de dados, ensaio de restauração e janela; preferir expandir → migrar dados → contrair. Rollback de frontend não equivale a rollback de banco.

O workflow manual [`homologate.yml`](../../.github/workflows/homologate.yml) prepara esse manifesto e reconstrói o banco descartável sem secrets. O job seguinte requer o environment `Homologação`, compara o SHA com a ponta atual de `main`, confere destino e digest, faz `db push --dry-run` e só então aplica as migrações pendentes em `CircuitoNE-dev`, sem seed/reset. Depois confere os privilégios padrão por conexão PostgreSQL com TLS verificado e registra também falhas. A concorrência serializa este workflow, mas não mudanças externas no banco entre o dry-run e a aplicação. A ausência da variável `HOMOLOGATION_DB_WRITE_ENABLED=true` causa falha explícita. Antes de habilitá-la, concluir o isolamento de credenciais da [#31](https://github.com/IgnisDevNE/CircuitoNE/issues/31) **e restringir o environment `Homologação` à branch protegida `main`**; as checagens no YAML não substituem essa regra, pois um workflow de branch pode ser alterado. O job não implanta a aplicação nem encerra [#32](https://github.com/IgnisDevNE/CircuitoNE/issues/32): ainda faltam schema de negócio, seed, smoke integrado e promoção controlada.
